## 1. ЦЕЛЬ ПРОЕКТА

Сканер, который **рисует прогноз** и работает в ДВУХ режимах:
1. **Засада** — заранее строит карту уровней/точек, ждёт прихода цены, при совпадении даёт сигнал (позже — оповещение в Telegram). Для Рагима, который на работе и не может следить за графиком.
2. **Живой прогноз входа** — прямо сейчас по текущей картине даёт тейк/стоп и расклад «можно входить».

Оба питаются одним: уровни (где насторожиться) + волны (докуда) + данные (когда).

**Философия — «ЗАРАНЕЕ → В МОМЕНТ», не «здесь и сейчас».** Старые сканеры реагировали на текущий момент → давали ≈ ноль (рынок уже в цене). Новый: гипотеза строится ПО ИСТОРИИ заранее, в тишине; живые данные лишь ПОДТВЕРЖДАЮТ её у точки. Эдж — в терпении (сканер ждёт у точки раньше всех), не в предсказании.

## 4. КЛЮЧЕВЫЕ ПРИНЦИПЫ ЧТЕНИЯ ГРАФИКА (его логика)

- **«Нет главного — все главные».** Ни один ТФ/индикатор/данные не главнее. Не голосование и не баллы — голоса ВКЛАДЫВАЮТСЯ друг в друга. Вывод — картина с развилками, не приговор.
- **Характер монеты — НЕ константа** (как настроение, может смениться). Измеряем текущее состояние + историю смен, не вечное число. Нет эталонной монеты — параметры относительные.
- **База графика — ОДНА линия по центрам 5m** (середина тела свечи), сужается геометрически до нужного ТФ (допуск = «старшесть ТФ»). Свечи не рисуем. Изгибы линии = вершины/впадины (отдельный зигзаг не строим). По 5m-версии не работаем — только сырьё; рабочие ТФ (1H/4H) = сужение. Прежний «зигзаг по разворотам» срезал ступени — отвергнут.
- **Скелет = этажи + линия вместе.** Этажи — горизонтальные зоны (не линии!), куда садятся макушки/впадины в разное время; роль меняется (поддержка↔сопротивление). Тело/тень не критерий — уровень это ЗОНА с допуском. Углы линии должны касаться этажей.
- **Уровни имеют СРОК ЖИЗНИ и работают ВПЕРЁД.** Живут, пока макушки садятся на них; сместились на новое расстояние — истёк. Старший ТФ → сильнее и дольше. Уровень из прошлого = действующая ловушка в будущем (цена бьётся о него позже). В трендах уровни игнорируются.
- **Ступени/волны — ритм (характер).** Волна = вершина→дно; коррекции в замере игнорируются, но их длина запоминается (где начнётся след. волна). Волны часто равны и их счёт устойчив (обычно 3, бывает больше). По ритму — проекция «докуда дойдёт» и «опоздавший вход» (зная остаток пути, входить выгодно даже с опозданием). Меряется геометрией (соразмерность отрезков ~±15% по глазу), НЕ в цене.
- **Передышки** внутри импульса (застой на свечу-две) несут характер: пробила → разворот, отбилась → коррекция. Ценнее, когда на уровне. Масштабны: на 4H не видны, на 1H точка, на 5m целое событие → находить на среднем ТФ, читать на младшем.
- **Скорость = длина свечей.** Длинные = рывок/энергия, короткие = «ползёт» (скучная монета, невыгодно — отсеивать). Длинные тени = рискованно.
- **Точка входа = где GEOMETRY и ДАННЫЕ согласны.** График = «где», данные = «сейчас». Данные = ВСЕ в сканере (RSI, MACD, StochRSI, MFI, ADX, BB, OI, funding, L/S, стакан, объём, Фибоначчи). Роль уровня (support/resistance) тоже сверяется с данными.
- **Прогноз** = пунктир по диагонали в пустоту, БЕЗ дат, до конечной точки; путь — ступенями-зигзагами по уровням. Умирает: нарушил путь / устарело основание (сдвиг параметров, не таймер) / заменён новым.

## 5. АРХИТЕКТУРА (три этапа)

1. **Предрасчёт по истории** (заранее, редко, СОХРАНЯЕТСЯ как свечи): фигуры, закономерности → «характер монеты», интересные зоны, при каких параметрах фигура сработала/оказалась ложной. Кэш карт: застывшее ядро + живой край (пересчитывается только край).
2. **Реальный анализ** (по текущему времени + готовая история): прогноз + зоны засад на часы–дни.
3. **Ожидание + КОНТРОЛЬ прогноза**: не тупо ждать, а сверять рынок с прогнозом; отклонение → сигнал «прогноз неудачен». Повторные сигналы = ошибка в логике/истории → чинить.

**Бюджет вычислений:** тяжёлое (карты) — редко, заранее, по событию закрытия бара, кэш. Лёгкое (сторож) — часто, сравнение чисел. Боевой сканер НЕ рисует (рисунки — только окно для человека). Живая часть = сервер (HTML не может: сторож должен жить всегда, реестр засад переживать рестарты, год истории не тянется браузером). Масштаб (сотни монет) не проблема при этой архитектуре.

## 6. ДАННЫЕ И ИНСТРУМЕНТЫ (что уже есть)

- **RK_LOADER** (Node.js) — готов, работает. **Консольный инструмент (CLI): Рагим запускает его ВРУЧНУЮ из командной строки Windows (cmd), не файлом-кнопкой.** Качает/дополняет архив **RK_DATA_v3** на локальном диске Рагима.
  - Запуск (Windows cmd, из папки загрузчика): сначала `npm install` (один раз), затем ПЕРВОЙ строкой `set RK_DATA_DIR=C:\путь\RK_DATA_v3`, потом `node index.js <команда>`.
  - Команды: `candles` (5m), `funding`, `ratios`, `oi`, `check` (проверка целостности), `plan` (оценка объёма/времени), `all` (весь цикл). Флаги: `--symbols=A,B`, `--archive-only`.
  - Первая закачка свечей — долгая (часы). Порядок обычного обновления раз в 3–4 недели: ratios, oi, funding, candles, check (ratios/oi/oi невосстановимы за окном 30 дней — дополнять вовремя).
  - Формат свечей RKB1, **10 колонок** (openTime, OHLC, baseVol, quoteVol, trades, takerBuyBase, takerBuyQuote), самоописанный, помесячно `klines_5m/<SYMBOL>/<YYYY-MM>.bin`.
  - Код RK_LOADER лежит в GitHub-репозитории `KaribovR/RK`, папка `Loader/`, и подключён к проекту синхронизацией. Структура: в корне `index.js`, `config.js`, `package.json`; `lib/` — archive, binance, log, rkb; `commands/` — candles, funding, ratios, oi, integrity, plan, universe.
- **Универсум** — растущее объединение: топ-150 по обороту ∪ все монеты архива (survivorship, делистнутые сохраняются). Юникод-имена монет реальны (напр. 龙虾USDT) — учитывать.
- **funding/ratios/oi** — НЕВОССТАНОВИМЫ за пределами окна (ratios/oi ~30 дней у Binance). Только копим; применять для анализа — не раньше ≥200 дней накопления. Загрузчик их дописывает, не перезатирает; каждая кнопка трогает только свою папку.
- Архив 5m → ресемплинг всех ТФ одним кодом (единый источник, бэктест=бой).
