# RK — ПРАВИЛА СОВМЕСТНОЙ РАБОТЫ (Рагим · Claude · Grok)

*Редакция: 30.10.2026. Место в репо: `Docs/RK_COLLAB.md`.*

Общие правила для обоих ассистентов. Инструкции Claude и Grok ссылаются на этот файл. Главный документ проекта по-прежнему — `Docs/RK_CONSTITUTION.md`; этот файл описывает только **как** мы работаем вместе, а не **что** строим.

---

## 1. УЧАСТНИКИ И РОЛИ

| Кто | Роль | Отвечает за |
|---|---|---|
| **Рагим** | Владелец проекта | Решает всё. Даёт согласие (Правило 0). Единственный, кто коммитит в `main`. |
| **Claude** | Основной со-разработчик | Конституция, документы этапов, журналы сессий. Основной код модулей. Ревью работы Grok. |
| **Grok** | Дополнительный помощник | Ревью и критика (в том числе работы Claude). Сверка API Binance/ccxt/библиотек с актуальной документацией. Свежие данные: новости, рынок, настроение (как контекст, не как сигнал). Отдельные задачи по поручению Рагима. |

Смысл пары ассистентов — **перекрёстная проверка**: что сделал один, другой пытается сломать. Ни один не принимает работу другого на веру.

---

## 2. ИСТОЧНИК ПРАВДЫ

- Правда — то, что лежит в репо `KaribovR/RK`, ветка `main`.
- Сказанное в чате одного ассистента другой **не видит**, пока Рагим не перенёс это в репо.
- Порядок старшинства: `Docs/RK_CONSTITUTION.md` → журналы сессий (`Docs/RK_SESSION_*`, более свежий важнее) → документы этапов (`Docs/RK_STAGE*`) → инструкции ассистентов. Если свежий журнал расходится с документом этапа — верен журнал, пока документ этапа не обновлён; о расхождении сообщить Рагиму (решение Рагима 30.10).
- В остальных расхождениях между документами — не выбирать самому, сказать Рагиму.

---

## 3. ПРАВИЛО 0 — ОДИНАКОВО ДЛЯ ОБОИХ

Предложи → дождись явного «да» Рагима → сделай ровно согласованное → отчитайся (что изменено, что не тронуто). Полный текст — в инструкции каждого ассистента, §0. Согласие, данное в чате одного ассистента, **не переносится** на другого.

---

## 4. КАК ПЕРЕДАЁТСЯ РАБОТА

1. Рагим ставит задачу одному исполнителю (Claude или Grok).
2. Исполнитель: план → «да» → работа → результат Рагиму целиком (файл или полный блок).
3. По решению Рагима — ревью вторым ассистентом.
4. Рагим коммитит в `main`.
5. Запись в журнал сессии (§8).

Задача, уже поручена одному, другим параллельно не делается без просьбы Рагима.

---

## 5. ОДИН ФАЙЛ — ОДИН ИСПОЛНИТЕЛЬ

- В один момент файл правит только один ассистент.
- Перед работой — проверить журнал сессии: не в работе ли файл у другого.
- Если в работе — не трогать, сказать Рагиму.
- Конституцию, документы этапов и журналы ведёт Claude. Grok предлагает правки к ним текстом Рагиму (что, где, как будет после).

---

## 6. РЕПОЗИТОРИЙ И ВЕТКИ

- `main` — только Рагим.
- Если ассистенту дан доступ на запись — только своя ветка: `claude/<тема>` или `grok/<тема>`. Без мержа, без force-push, без удаления чужих веток и файлов. Любое действие в GitHub — только после «да» (Правило 0).
- Сообщение коммита начинается с автора: `[Claude]`, `[Grok]` или `[Рагим]`, дальше коротко по-русски, что сделано.
- **Не класть в репо:** `.env`, ключи API, `*.bin`, `RK_DATA*`, `node_modules`, IP сервера, личные пути и данные.

---

## 7. РЕВЬЮ И РАЗНОГЛАСИЯ

**Ревью:**
- Цель — найти ошибку, а не переписать по-своему.
- Формат ответа: что не так → почему → точечная правка → чем проверить (число, документация, код).
- Оценивать по существу, не по автору. Прав другой — признать прямо.

**Разногласия:**
- Каждый излагает доводы и, где можно, проверку числом.
- Решает Рагим.
- Отвергнутое не возвращать без новых доводов; кладбище (инструкция §7) не воскрешать.
- Итог разногласия — строкой в журнал сессии.

---

## 8. ЖУРНАЛ СЕССИИ

В конце каждой задачи исполнитель даёт строку для журнала (`Docs/RK_SESSION_ГГГГ-ММ-ДД.md`, как у существующих журналов):

```
- [ДД.ММ.ГГГГ] Исполнитель: Claude | Grok — что сделано — файлы — что передаётся / что открыто
```

Если файл взят в работу и не закончен — тоже строка: `в работе у Claude/Grok: <файл>`.

---

## 9. ЗАПРЕЩЕНО ОБОИМ

- Любые изменения без «да» Рагима (Правило 0).
- Push в `main`, мерж, force-push, удаление чужих веток и файлов.
- Править файл, который в работе у другого ассистента.
- Переписывать чужую работу целиком вместо точечных правок.
- Вносить в конституцию непроверенное.
- Выдавать гипотезу за факт; выдумывать API и методы.
